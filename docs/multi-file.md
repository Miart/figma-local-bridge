# Мультифайловая поддержка: несколько открытых файлов Figma на один мост

> Статус: **реализовано.** Код-референс — `gethopp/figma-mcp-bridge`
> (MIT): реестр соединений по `fileKey`, `list_files`, опциональный `fileKey` в
> каждом инструменте. У нас этому соответствует `Daemon` в `server/src/link.ts`.
> Тесты — `test/multifile.test.mjs` и `test/multifile.e2e.mjs`; решения по
> открытым вопросам и отступления от дизайна — ниже.

## Зачем

Сейчас плагин спаривается ровно с одним сокетом: второе окно Figma получает
`4409 already paired` («another Figma window holds the plugin slot»). Любая работа,
где файлов два — ассеты в одном и макеты в другом, сравнение двух файлов,
параллельные агенты по разным файлам — требует закрыть панель в первом.

gethopp показывает, что ограничение снимается без потери инвариантов: один
WebSocket-порт, но **реестр соединений, ключ — `figma.fileKey`**, и маршрутизация
запроса по файлу.

## Что НЕ меняется

- один демон, один порт `8787`, один plugin-токен, один info-файл;
- `opId`-идемпотентность, `rev`, scope-guard, `Dispatcher` — всё живёт **внутри
  плагина**, а у каждого файла свой экземпляр плагина и свой dispatch. Ничего не
  трогаем;
- MCP-клиенты по-прежнему аттачатся к демону по `clientKey`; неймспейсинг id
  запросов (`<cid>:<id>`) и адресный `broadcast` — без изменений.

Меняется только «сколько сокетов держит демон и как выбирается адресат».

## Протокол

### 1. Плагин называет свой файл при подключении

```
ws://127.0.0.1:8787/?role=plugin&token=<token>&fileKey=<key>&name=<fileName>
```

- `figma.fileKey` определён **только у сохранённых файлов** (`null` у нового
  несохранённого). Fallback — сессионный ключ `unsaved-<base36>-<rand>`,
  сгенерированный один раз на iframe и закэшированный (`plugin/code.ts`);
  повторный reload панели в том же окне сохраняет ключ.
- `name` = `figma.root.name` — только для сообщений об ошибках и панели.

### 2. Демон: реестр вместо одного слота

`server/src/link.ts`:

```ts
private plugins = new Map<string, { ws: WebSocket; name: string; saved: boolean }>();

// onConnection, role=plugin:
//   токен проверяется как сейчас;
//   НЕ 4409: повторный коннект с тем же fileKey закрывает старый сокет
//   (reload панели, перезапуск плагина) и занимает его место:
if (this.plugins.has(fileKey)) this.plugins.get(fileKey)!.ws.close(4409, "replaced by a newer socket");
this.plugins.set(fileKey, { ws: socket, name, saved: fileKey.startsWith("unsaved-") === false });
```

- heartbeat (`startHeartbeat`) перебирает `plugins.values()`; мёртвый сокет
  терминируется и удаляется **только он**, остальные файлы не задеты;
- лимит файлов (предлагаю 16): сверх — `4413 too many files`, с логом. Смысл —
  предсказуемая память и внятная ошибка вместо тихой деградации;
- при pair/unpair рассылается новое событие:

```json
{ "id": null, "event": "files",
  "files": [{ "fileKey": "abc123", "name": "Example File", "saved": true }] }
```

`event: "link"` сохраняется, но теперь означает «есть хотя бы один файл» —
старые клиенты не ломаются. Добавляется адресное `{event:"file", fileKey, connected}`
для мгновенного отказа вызовов **одного** файла при его обрыве (сейчас
`FigmaClient.onEnvelope` рвёт всё сразу — при мультифайле это будет резать чужие
запросы).

### 3. Маршрутизация запроса

Конверт получает необязательное поле `file`:

```json
{ "id": "<cid>:<n>", "method": "get_screenshot", "params": {...}, "opId": "...", "file": "abc123" }
```

Правила в демоне (единственный авторитет):

| `file` | файлов подключено | действие |
|---|---|---|
| указан | есть такой | в его сокет |
| указан | нет такого | **немедленный** ответ-ошибка: `{id, ok:false, error:{message:"No plugin connected for fileKey … Connected files: …"}}` |
| не указан | 1 | в него (обратная совместимость) |
| не указан | 0 | ошибка `FIGMA_BRIDGE_OFFLINE` (как сейчас) |
| не указан | >1 | ошибка со списком: `Multiple files connected. Specify fileKey: "A" (abc123), "B" (def456). Use figma_ping to see them.` |

Ключевое: нерезолвящийся запрос получает **ответ об ошибке**, а не висит до
таймаута. Демон отвечает тем же конвертом (`ok:false`), что и плагин, — клиент
разбирает его существующим кодом.

### 4. MCP-слой

- `FigmaClient` кэширует список файлов из события `files` и **сам** отказывает
  до отправки, когда файл очевиден из состояния («укажи fileKey») — дешёвая и
  точная ошибка; демон остаётся страховкой от гонок;
- `FigmaClient.selection` становится `Map<fileKey, SelectionState>`; событие
  `selection` несёт `file`;
- `client.call(method, params, timeoutMs, fileKey)` → `link.send({..., file: fileKey})`;
- в каждый tool добавляется параметр (22 инструмента, по строке):

```ts
fileKey: z.string().min(1).optional()
  .describe("Which connected file; required when more than one is connected. See figma_ping."),
```

- `figma_ping` возвращает `files: [{fileKey, name, saved}]` и выбранный файл;
- при мультифайле `figma_whoami`/`figma_get_selection` без `fileKey` — та же
  ошибка «specify fileKey», не угадывание.

### 5. Плагин и панель

- `plugin/tools.ts` не меняется: методы выполняются в контексте своего файла;
- `plugin/ui.html`/`code.ts`: в URL подключения добавляются `fileKey` и `name`;
  панель продолжает показывать свой файл, ей ничего не нужно знать про соседей.

## Совместимость и миграция

1. Плагин и сервер лежат в одном репо и обновляются вместе; старый плагин без
   `fileKey` регистрируется как единственный файл (`legacy plugin`) и работает
   как раньше (клиент без `files`-события считает, что файл один).
2. Порядок выката: `link.ts` + тесты → `figma.ts` + тесты → tools + README.
3. `README.md` (секция «Several files at once»): «второй **файл** подключается
   тем же плагином в другом окне; второй **демон** по-прежнему нельзя».

## Решения (были открытые вопросы)

1. **Лимит файлов** — 16; переполнение — отказ новому (`4413 too many files`),
   без вытеснения старого.
2. **Дефолт при мультифайле** — всегда явный `fileKey`; отказ происходит **до
   отправки** (клиент по кэшу `files`, демон независимо — как страховка от
   гонок).
3. **Имя параметра** — `fileKey`, как у официального сервера и gethopp.
4. **Событие `files` в hello-пакете** — добавлено: аттачащийся клиент сразу
   получает снимок реестра.
5. **Панель** — «подключено файлов: N» не показываем.

## Отступления от дизайна (по факту реализации)

- у несохранённого файла свой ключ `unsaved-<rand>` (плагин генерирует один раз
  на iframe и кэширует), а не общий `legacy`;
- `fileKey` — только маршрутизация: `callWithMeta` вырезает его из `params`,
  плагин его не видит;
- при обрыве файла его in-flight вызовы отклоняются сразу и помечаются
  `bridgeNoRetry` — MCP-клиент не ретраит их вслепую;
- `figma_ping` при нескольких файлах отвечает списком с пометкой, а не ошибкой.

## Оценка

| Часть | Diff |
|---|---|
| `server/src/link.ts` (реестр, маршрутизация, heartbeat, события) | ~150 строк |
| `server/src/figma.ts` (selection-map, `fileKey` в call, быстрые отказы) | ~40 |
| `server/src/*-tools.ts` (`fileKey` в 22 инструментах) | ~25 |
| `plugin/code.ts` + `ui.html` (URL) | ~15 |
| Тесты | ~150 |
| README | ~20 |

Риск средний: меняется горячий путь демона, но слой идемпотентности и
транзакционности не затрагивается. Обратная совместимость при одном файле —
полная.
